# AGENTS.md

Guidance for human and AI contributors working in this repository.

## Project purpose

This repo is the **Nakama research dashboard plugin**: one dashboard page plus five agent tools over a
research knowledge base (topics → development axes → the evidence attached to them). It is the source of truth
for that product; the *estate* (service blocks, compose files, instance config, agendas) lives outside it and is
not maintained from here.

The repo is **public**. Its acceptance records, montages and screenshots are read by reviewers who have only a
clone, so everything committed here is written to be read from a clone and to carry no personal or machine
identity (see *Public-record hygiene*).

Status: **UX-v2 composition phase complete** — composition C1–C5 accepted, H1 keyboard focus accepted, baseline
tagged `ux-v2-composition-complete`. `docs/ux-v2/` holds the product decisions and unit docs;
`docs/reviews/` holds the acceptance records that closed each unit.

## Orientation

| Path | What it is |
|---|---|
| `src/ui.tsx` | the dashboard page: components, the stylesheet (in a template literal), the composition |
| `src/actions.ts` | the agent tools (Nakama plugin actions) |
| `ui/app.js`, `actions/` | **committed build output** — regenerated by `bun run build`, never hand-edited |
| `nakama.plugin.json` | the plugin manifest: ids, tool declarations, migrations list |
| `migrations/` | SQL migrations; **must be declared in the manifest** or the host never runs them |
| `skills/` | the **shipped** plugin skill (what the plugin's own users' agents load) |
| `harness/` | the acceptance harness: passes, guards, install/reinstall helpers, focus matrix |
| `vendor/` | the one-line allowlist patch + the script that places the plugin into a Nakama checkout |
| `docs/ux-v2/` | composition docs, `DECISIONS.md` (the standing decisions), unit docs, fidelity reviews |
| `docs/reviews/` | per-unit acceptance records (reviewer verdicts verbatim) |
| `docs/corpus/`, `docs/layout-fixtures/` | the committed acceptance transcripts and screenshots |
| `.agents/skills/` | **contributor procedures** for this repo (see *Skills*) |

Two different things are called "skills" here and they must not be confused: `skills/` is a **product
artefact** — the skill Nakama serves to the plugin's users — while `.agents/skills/` holds **contributor
procedures** that never ship.

## Tooling

- **Bun only** (`bun`, pinned by `bun.lock`). There is no npm/yarn/pnpm workflow and no `node_modules` step to
  run by hand; `bun install` is all there is.
- TypeScript is checked two ways: `typecheck` (`tsc --noEmit` over the sources) and `typecheck:host`
  (`harness/typecheck-host.mjs`, which checks against the host's own plugin types). A build that compiles is not
  a build whose types were verified — run both.
- The browser harness uses `playwright-core` with a cached Chromium resolved by the harness itself.

## Common commands

| Task | Command |
| --- | --- |
| Everything the merge gate runs | `bun run check` (typecheck + build + unit tests) |
| Types only | `bun run typecheck` · `bun run typecheck:host` |
| Rebuild the committed output | `bun run build` |
| Unit tests | `bun run test` |
| Acceptance pass (read) | `bun run harness:read` (corpus) · `bun run harness:fixture` (fixture) |
| Acceptance pass (write) | `bun run harness:write` (fixture, mutates — reseed afterwards) |
| Keyboard-focus pass | `bun run harness:focus` |
| Dataset-identity classifier | `bun run harness:identity` |
| Public-record redaction guard | `bun run harness:records` |
| Install / refresh the plugin in a checkout | `bun run harness:install` · `bun run harness:reinstall` |
| Replay the corpus into an instance | `bun run harness:seed` |

The passes take `--dataset`, `--viewport` and (for the focus pass) `--negative-control`; they can be invoked
directly as `bash harness/read-pass.sh …` / `bash harness/focus-pass.sh …` when a non-default combination is
needed.

## Build → vendor → serve: the loop

A source change reaches a running instance through **four** steps, in this order. Skipping one is the usual
cause of "the fix is in the code but not on the page":

1. `bun run check` — build and tests together; the gates are not optional.
2. `./vendor/vendor-into-nakama.sh <nakama checkout>` — places the built output into the checkout the instances
   install from.
3. `bun harness/reinstall-plugin.mjs --env-file <instance env file> --org-id <org id>` — mints the release and
   rebinds the named org. **Name the organization explicitly** (`--org-id` / `--org-name`, or `NAKAMA_ORG_ID` /
   `NAKAMA_ORG_NAME`): on a multi-org account the helper refuses rather than rebinding `orgs[0]`, which is how a
   fixture reinstall once rebound the wrong organization. A single-org account still falls back to its only org.
4. **Verify with the guard**, not with the reinstall's own output:
   `bun harness/served-build-guard.mjs` (it fetches the asset the browser actually fetches). If it still reports
   the previous release, restart that instance's web and API units and re-check — do not conclude the change
   failed to apply, and do not record anything until the guard is green.

**Take the instance's URL, port and env file as one parameter set.** The corpus env file carries no
`NAKAMA_URL`, so a tool that defaults to it inherits whatever the caller's shell happens to hold — an earlier
session's sourced env file will redirect a "corpus" reinstall to the fixture, and the reinstall will report a
new version while the old bytes are still served. Pass it explicitly:

```bash
env NAKAMA_URL=http://127.0.0.1:4399 \
    NAKAMA_EMAIL="$NAKAMA_SEED_ADMIN_EMAIL" NAKAMA_PASSWORD="$NAKAMA_SEED_ADMIN_PASSWORD" \
    bun harness/reinstall-plugin.mjs
```

Related, same class of trap: sourcing a compose env file with `set -a` reframes *every* variable it defines. If
one of them is `PATH`, your toolchain disappears mid-command (`bun: command not found`), and a pipeline
(`bun … | tail -3`) hides the failure because the pipeline exits with the last command's status. Restore `PATH`
and re-run the gate; then confirm the commit or tag actually landed rather than trusting the chain.

**Build identity is the digest folder**, not the vendored tree: `0.2.0+dev.<digest>`, with a per-instance
revision that moves even when the bytes do not. Quote both, plus `ui/app.js`'s sha256, when a record claims
which build it measured.

## The acceptance pass

The pass drives a real browser against a served instance and writes a **transcript** that is committed as
evidence. Its contract:

- **Exit `0` and exit `1` are verdicts** — the transcript replaces the committed record, green or red.
- **Exit `2` (ABORTED) and exit `3` (REFUSED)** leave the committed record untouched: the run did not establish
  anything, so it must not overwrite something that did.
- **The served-build guard is a precondition.** If the instance is not serving this build, the pass refuses
  rather than recording a result about unknown bytes.
- **Dataset identity is checked, not trusted.** The pass separates corpus, fixture and the write pass's own
  `ui-check` residue, and refuses an empty store. Never record a fixture run as a corpus one: the transcript
  path encodes dataset and viewport precisely so that cannot happen by accident.
- **Superseded records are archived, not discarded.** When a record is re-taken on a new build, preserve the
  previous one as `*.revision-<n>.txt` (the instance revision it was taken at) — in the tag that carries
  that build, not on the tip. The tip keeps one canonical record per dataset and viewport; recover a
  checkpoint with `git show <tag>:docs/corpus/verify-read.txt.revision-511.txt`.
- **The write pass mutates the fixture.** It is the canonical composition-inside-a-write record; label it
  canonical, and re-seed before the next ordinary fixture run.
- **The screenshots are the pass's own output.** It republishes them on every run, so a pass run will show
  screenshot changes; check whether they are yours before committing them.

## Evidence discipline

- **"Verified, not assumed"** — an instance-state claim is made from a fresh measurement or not at all. Prefer
  the guard, the classifier and the transcript over reasoning about what *should* be served.
- **Label what kind of claim it is.** A design-review hypothesis and a tested measurement are different things
  and are recorded as such. A record states the build it measured, the dataset, and the viewport.
- **Cross-verify reports from other agents and other machines** instead of trusting them; a summary is not
  evidence.
- **Never mask a runtime failure to get a green run.** If the store throws (e.g. SQLite
  `SQLITE_BUSY_RECOVERY` / `database is locked`), record the lost run as its own event and re-run; sleeps that
  hide a lock are not a fix, and that debt is tracked separately, not closed by a passing suite.

## Public-record hygiene

Everything here is public, so a record carries **labels, never live endpoints** (`docs/ux-v2/DECISIONS.md` §11):

- loopback stays verbatim (`127.0.0.1:3005` identifies nobody and is a useful diagnostic);
- an identity-shaped host becomes the placeholder `http://<box>.<tailnet>.ts.net` (scheme, port and path kept);
- a literal address, a private DNS suffix (`.ts.net`, `.local`, `.internal`, `.lan`) or `os.hostname()` is
  redacted; `.home` is deliberately **not** a private suffix (it collides with `process.env.HOME`);
- public hosts (the GitHub remote, upstream docs) are left alone.

**The rule lives at the emitter.** Both emitters route through `harness/redact.mjs`, and `bun run harness:records`
asserts the rule *and* scans the whole public tree for identity-shaped text. Fixing only the committed files
guarantees the next pass re-creates the leak.

- **Credentials are referenced by key name, never by value** — no secrets, tokens or passwords in files,
  transcripts or commit messages. The live values belong to the instance env files, which live in the estate.
- **Published history is not rewritten.** A correction lives in a document, not in a force-push; rewriting is a
  decision taken explicitly, with its cost (every commit hash, every clone and fork) stated.

## Keyboard focus

The page's focus treatment is a **product rule**, not styling detail (`DECISIONS.md` §12): one indicator for
every control, from one rule in the plugin's token block, judged by what the render achieves — the WCAG 2.1
non-text minimum of **3:1** against the surface it is drawn on (measured at 4.61:1 on the muted card and 5.02:1
on white).

- Measure **per control class**, sampled across views, with real `Tab` presses — never `element.focus()`, which
  does not match `:focus-visible` and measures a state no keyboard user sees.
- **Read the settled render**: Tailwind's `transition-colors` includes `outline-color`, so a computed style read
  at the instant of focus is a mid-transition value (one control read 2.04:1 mid-transition and 4.61:1 once its
  animations had finished). Wait on the element's own animations, never a blanket sleep.
- **A green run must be able to go red.** `--negative-control` injects CSS that removes every indication and
  requires the per-class checks to fail; a suite that cannot see a removed indicator proves nothing by passing.
- Report unreached instances honestly (scroll containers are in the tab order only while they overflow, and a
  re-rendering pane changes the count); **assert class coverage**, report instance arithmetic.

## Records and docs

- **A standing decision goes in `docs/ux-v2/DECISIONS.md`**, numbered and dated, with the reason — not in a
  commit message alone.
- **A unit's own doc** goes in `docs/ux-v2/<unit>.md`; its acceptance record in
  `docs/reviews/<date>-<unit>-acceptance-record.md`, carrying the reviewer's verdict **verbatim**, the measured
  before/after, and the explicit boundaries.
- **A gate or a rule needs an executable assertion**, not prose: if a claim can be checked, it belongs in
  `bun run check` or a `harness:*` suite.
- **Boundaries are stated, not implied.** Where something is out of reach (a host-owned control, a retired
  finding's subject), the record says so, so a reader does not mistake silence for coverage.

## What is tracked

Evidence accumulates faster than source, so the checkout carries three buckets (policy set 2026-10-03):

- **Tracked permanently** — source, tests, migrations, the bundles install needs (`ui/app.js`, `actions/`),
  the datasets' seed and provenance, the approved prototypes, the current canonical screenshot and acceptance
  transcript per dataset and viewport, and the final acceptance records.
- **Generated, never tracked** — side-by-side montages and their HTML wrappers, write-pass screenshots,
  preview montage packs, per-iteration visual comparisons. If it can be rebuilt from the first bucket it
  belongs in `.gitignore`, not in the index.
- **Preserved by tag, not by the tip** — superseded checkpoints (`*.revision-<n>.txt`), earlier stage
  transcripts, implementation diaries, review correspondence. A tag already carries them, and
  `git show <tag>:<path>` recovers one, so the tip keeps only the current canonical set.

Two follow-ups are recorded rather than done: the write pass still publishes into the read-shot directory
instead of a scratch directory (`read-pass.sh` uses one `DEFAULT_SHOTS` for both passes, so `.gitignore`
rules hold the line), and the derived prototype/montage packs under `docs/ux-v2/fidelity/` stay
harness-coupled while that area is in active visual use.

## Commits and tags

- Commit messages are imperative and **evidence-bearing**: what changed, what was measured, which build. The
  body carries the numbers a reviewer will want, not a narrative of the session.
- **Annotated tags carry their own summary** and point at the commit that carries the record — not at the
  implementation commit before it, when a documentation commit follows.
- **Never move, delete or force-push a tag**; a new baseline gets a new name (`ux-v2-complete` stays on the
  pre-composition baseline; `ux-v2-composition-complete` marks the phase close).
- **Never force-push `main`.** It is the published source of truth and reviewers work from it.

## Plan-first tasks and draft PRs

New coherent work is planned before it is implemented, on a **branch per task**, so a reviewer can
judge the intent before the diff and a fresh session can resume from the PR alone. This is the default
for a new task; it is not a ceremony for a one-line fix.

- **One branch, one task.** Each coherent change gets its own branch off `main` (the skills and path
  hygiene for one area is one task; an unrelated fix gets its own branch and its own PR). Never commit
  or work directly on `main`.
- **Plan first, and commit the plan.** The plan is minimalist and versioned — goal, scope, acceptance
  criteria, explicit exclusions — under `docs/plans/<date>-<slug>.md`. It is a public, tracked,
  sanitized record like every other document here. Machine- and service-specific operational detail
  (instance parameter sets, env keys, private paths) is an *appendix* that stays in the ignored
  `.hermes/plans/` scratch, never in the committed plan.
- **Open the PR as a draft right after the plan commit**, so the plan is the PR's first reviewable
  artefact and the diff grows against a stated intent.
- **The PR body states scope, acceptance and exclusions** — what the PR does, how it is judged done,
  and what it deliberately leaves out (the *Boundaries are stated, not implied* rule at PR scale).
- **Commits stay incremental and evidence-bearing** (see *Evidence discipline* and *Commits and tags*);
  nothing lands unmeasured.
- **Resume a task in a fresh session from the PR** — its diff, the committed plan and the review
  comments — not from session memory. The PR is the durable handoff.
- **Mark ready for review once the gates pass** (`bun run check`, plus the relevant `harness:*` suite),
  and **merge only after review, at the exact head that passed CI**; do not enable auto-merge ahead of
  the reviewed head.
- **A manual or fixture-evidence PR carries the approved packet and the findings, never a database
  snapshot.** Commit the seed procedure and the transcript that reproduce the state; the live store is
  local and stays local.
- **Forward-looking by design.** A completed, published stage is not retrofitted with a branch or PR,
  and published history is not rewritten to conform (see *Public-record hygiene*). A new task starts
  the loop again.

## Skills

Contributor procedures live in **`.agents/skills/`** — the cross-client Agent Skills layout (`SKILL.md` plus
`references/`, `scripts/`, `assets/`), versioned with the code so a clone carries the project's *procedures*,
not only its source. Read the relevant one before touching the area it governs; when a lesson is learned here,
update the copy here.

- `dashboard-build-and-serve/` — the build → vendor → reinstall → guard loop, instance parameter sets, and the
  identity a record must quote. Read before changing anything that reaches a served instance.
- `acceptance-pass/` — the pass's exit contract, dataset identity, transcripts, archiving and re-seeding.
- `public-records-hygiene/` — the redaction rule, the guard, and what to do when a leak is found.
- `keyboard-focus-pass/` — the focus measurement recipe and the four traps that make it lie.

**Hermes needs the project trusted once per machine**, from the repository root:

```bash
hermes skills trust "$(git rev-parse --show-toplevel)"   # once per machine
```

**Nothing here is vendored from another repository, so there is no `skills-lock.json` to keep in step** — a lock
file exists to pin skills taken from elsewhere (the estate's `udv-echo-process` carries one for the two it takes
from upstream). Everything in `.agents/skills/` is written for this repo and reviewed here.

**Do not let these fork with the profile-global skill.** The generic craft of *authoring a Nakama plugin*
belongs to the Hermes skill `nakama-plugin-development` (outside this repository, maintained by the agent); the
procedures for *this plugin, this harness, these records* belong here. A project-local skill **shadows** a
global skill of the same name (first-wins deduplication), so a same-named repo copy silently hides the newer
global one — which is why the skills above are named for this repo's procedures rather than reusing the global
name. Rename rather than re-introduce a collision.

`.hermes/` is git-ignored on purpose: agent working artifacts, never repository documentation. **Scratch files go
in `.hermes/scratch/`**, never directly in `.hermes/` — Hermes' write guard treats any file whose immediate
parent is a project-local `.hermes` as agent-steering config and asks a human to approve each write there.

## Scope boundaries

- This repo is the **plugin**. The estate's compose files, instance env files, service docs and agendas live
  outside it; the estate is a local repository with no remote by design, and its review handoffs never include
  it. Only this repo is pushed.
- The knowledge-base ingestion/enrichment pipeline is a **separate project**; do not grow it into this repo.
- `docs/` is documentation for a reader with a clone. Nothing in it should require the author's machine to
  interpret.
