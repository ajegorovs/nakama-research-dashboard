**Status:** decisions accepted; both folded into [`../V2-PLAN.md`](../V2-PLAN.md) §7 as **D8** and **D9**.
**Context:** the C3 handoff left two items open for the reviewer — what evidence a manual status change

---

C3 looks properly closed. The tool surface, provenance, nested schema validation, and end-to-end agent
exercise are now in much better shape than the original plugin.

On the two C8 questions:

1. **Manual status change should carry an optional note/evidence field.** I would not require it for
   every human edit, but the UI should make it easy to add a short rationale. If someone changes
   `blocked → parked`, a note like "waiting intentionally for October hardware slot" is valuable because
   the librarian can read that later and avoid re-inferring `blocked`.

2. **Overview should present axes grouped under topics, not as a global flat list.** The scan pattern
   should be:
   - topic name
   - people tagged to topic
   - counts: active / blocked / draft / parked
   - then 2–4 most relevant axes
   - recent 14-day activity summary
   - expand for all axes/history

For axis ordering within a topic, I'd use roughly:
`blocked → active → draft → parked → completed → abandoned`, then most recently updated within each
group. That puts "needs attention" first without hiding ongoing work.

I'd start **C4 with the overview shell and topic cards**, then C8 can deepen topic detail/editing. The
current store already has enough structure for that; no schema change seems necessary.
